# GuIA — visão geral do projeto

> Documento vivo: mantido atualizado conforme o projeto evolui. Última revisão: 2026-07-26.

## 1. O que é o projeto

**GuIA** é um tutor educacional com IA, em formato de aplicativo desktop (Windows), desenvolvido como Trabalho de Conclusão de Curso (TCC). A ideia central é diferenciar o GuIA de um chatbot de IA comum: em vez de responder perguntas diretamente, ele usa o **método socrático** — conduz o aluno com perguntas até que ele mesmo chegue à resposta, em vez de simplesmente entregá-la pronta.

O objetivo acadêmico por trás disso é validar, com dados reais de uso, se uma IA que ensina por perguntas (em vez de responder) gera mais aprendizado real do que uma IA convencional que só responde — essa comparação é a tese do TCC.

Além do tutor para alunos, o app tem um **modo professor**: contas de professores (verificadas por um código de instituição) podem pedir ajuda direta — planos de aula, gabaritos, materiais — sem o filtro socrático, já que quem está do lado professor não precisa ser "protegido" de receber a resposta.

**Prazos combinados:**
- **28/09/2026** — ter os recursos abaixo implementados de forma simples e funcional (não precisa ser 100% polido).
- **Outubro/2026** — feira de ciências/amostra da escola.
- **Fim de novembro/2026** — apresentação de TCC (inclui a validação com participantes, que roda entre outubro e novembro).

## 2. Como funciona (visão simplificada)

1. O aluno abre o app, escolhe (ou cria) seu **perfil local** com senha.
2. Ele digita uma pergunta no chat.
3. Antes de qualquer coisa, a mensagem passa por um **filtro de segurança determinístico** (regras fixas) que bloqueia pedidos óbvios de má-fé (cola, gabarito, jailbreak) ou de conteúdo nocivo (violência, drogas, automutilação, conteúdo adulto).
4. Se passar, a mensagem vai para a **IA** (modelo de linguagem), junto com um "prompt de sistema" que instrui o modelo a **nunca entregar a resposta pronta** — só fazer perguntas, dar dicas, corrigir erros.
5. Se a pergunta envolve números (cálculo, conversão de unidade, tabela periódica), a IA usa **ferramentas determinísticas** (calculadora real em Python, não "de cabeça") para ter certeza dos valores antes de confirmar algo pro aluno.
6. A resposta final passa por uma **limpeza automática** (remove qualquer resíduo de código LaTeX que o modelo eventualmente escreva por engano) antes de aparecer na tela.
7. A conversa inteira é salva num banco de dados local, organizada por perfil — o aluno pode voltar, continuar de onde parou, renomear ou apagar conversas antigas.
8. Se o perfil for de um **professor** (verificado por código de instituição na criação do perfil), ele pode alternar pra um modo onde a IA ajuda diretamente, sem o filtro socrático.

## 3. Como funciona (em código)

### Fluxo de uma mensagem, arquivo por arquivo

```
ui/windows/guia_window.py (handle_send)
        │  usuário digita e envia
        ▼
ui/workers/ai_worker.py (AIWorker, QThread)
        │  roda em background pra não travar a UI
        ▼
app_controller.py (AppController.ask)
        │  1. detecta idioma (lang_detect.py) se config = "auto"
        │  2. chama o engine
        ▼
engine.py (TutorEngine.ask)
        │  1. checa limite de tamanho (config.py)
        │  2. checa segurança: safety.py (check_safety) — bloqueio determinístico
        │  3. monta histórico + prompt (prompt.py) + personalização
        │  4. chama o provider certo (com retry)
        ▼
providers/*.py (Groq / OpenAI / OpenAICompatible / LMStudio)
        │  chama a API de fato, com function-calling
        │  se o modelo pedir uma ferramenta:
        ▼
tools.py (calcular / converter / elemento)
        │  executa com segurança (AST, sem eval) e devolve o resultado
        ▼
engine.py
        │  limpa a resposta: latex_sanitizer.py (strip_latex)
        ▼
app_controller.py
        │  salva pergunta + resposta no banco: db/repository.py
        ▼
ui/windows/guia_window.py (on_ai_response)
             mostra o balão de resposta na tela
```

### Módulos centrais

| Arquivo | Responsabilidade |
|---|---|
| [`engine.py`](engine.py) | Orquestra a conversa: histórico, escolha de prompt/modo, retry entre providers, geração de título automático. |
| [`prompt.py`](prompt.py) | Os prompts de sistema: `SYSTEM_PROMPT` (aluno, completo), `SYSTEM_PROMPT_COMPACT` (aluno, versão enxuta pra modelo local pequeno), `PROMPT_PROFESSOR` (assistente direto), `PROMPT_LIBRARY` (conversa sobre artigo científico da Biblioteca — meio-termo entre aluno e professor). |
| [`safety.py`](safety.py) | Filtro determinístico (regex) contra má-fé óbvia e conteúdo nocivo — 2ª linha de defesa, não a principal (a principal é o próprio modelo entendendo intenção). Normaliza texto contra ofuscação (homóglifos, leet, espaçamento). `check_safety_verbose` também devolve qual padrão disparou, usado para registrar em `safety_blocks`. |
| [`tools.py`](tools.py) | Calculadora (AST seguro), conversor de unidades, tabela periódica — ferramentas que o modelo chama via function-calling, pra nunca "calcular de cabeça". |
| [`latex_sanitizer.py`](latex_sanitizer.py) | Rede de segurança: limpa resíduos de notação LaTeX que o modelo às vezes escreve por engano, convertendo pra Unicode/texto puro antes de mostrar na tela. |
| [`lang_detect.py`](lang_detect.py) | Detecção leve de idioma (PT/EN/ES) pra reforçar o idioma de resposta no modo automático. |
| [`app_controller.py`](app_controller.py) | Ponte entre UI e o resto do sistema: providers, perfis/login, modo aluno/professor, banco de dados, configurações. |
| [`auth.py`](auth.py) | Hash de senha (PBKDF2, stdlib) pros perfis locais. |
| [`user_config.py`](user_config.py) | Preferências do usuário (nome, idioma, tema, fonte, chave de API própria) — persistidas em JSON em `%APPDATA%/GuIA/config.json`. |
| [`config.py`](config.py) | Configuração de ambiente/dev: chaves de API do `.env`, limites de tamanho, flags de features, modo de coleta de dados da pesquisa (`STUDY_MODE`). |

### Banco de dados (`db/`)

SQLite local em `%APPDATA%/GuIA/guia.db`, via SQLAlchemy (troca de backend futura, ex. nuvem, é só mudar a connection string).

```
Institution (código de instituição p/ liberar modo professor)
User (perfil local: nome, role aluno/professor, senha com hash)
  └─ Conversation (título, provider usado)
       └─ Message (role, conteúdo, ordem)
            └─ SafetyBlock (registro de bloqueio — modelo pronto, ainda não populado)
```

- [`db/models.py`](db/models.py) — schema (SQLAlchemy).
- [`db/session.py`](db/session.py) — engine/conexão + migração leve de colunas novas (sem Alembic ainda).
- [`db/repository.py`](db/repository.py) — todas as operações de alto nível (única porta de entrada pro banco; o resto do app nunca importa `models`/`session` direto).

### Interface (`ui/`)

PySide6 (Qt). Janela principal em [`ui/windows/guia_window.py`](ui/windows/guia_window.py), que monta sidebar (histórico de conversas), área de chat (balões) e campo de entrada. Diálogos de login e configurações em `ui/dialogs/`. Trabalho pesado (chamada à IA, geração de título) roda em `QThread` (`ui/workers/`) pra não travar a interface.

### Providers (`providers/`)

Todos implementam a mesma interface (`chat(messages, system_prompt, max_tokens) -> str`), o que permite trocar de IA sem mexer no resto do código:
- `GroqProvider` — modelo principal (`openai/gpt-oss-120b`), tem tratamento especial pra tool-calls malformados em XML que o modelo às vezes gera.
- `OpenAIProvider` — fallback de dev.
- `OpenAICompatibleProvider` — genérico, cobre a chave de API própria que o usuário configura (Groq/OpenAI/OpenRouter/qualquer endpoint compatível).
- `LMStudioProvider` — modelo local grátis, sempre por último na ordem de prioridade (fallback sem custo).

## 5. Próximos passos e objetivos

**Bug real corrigido: mensagem "some" ao conversar sobre um artigo da Biblioteca (2026-09-08).** Matheus reportou: clicar em "Conversar no chat" a partir de um artigo, mandar uma mensagem, e nada aparece na tela — mas fechando e reabrindo o app, a mensagem e a resposta aparecem normalmente (ou seja, foi salva certinho no banco, só não renderizava ao vivo). Causa raiz encontrada via reprodução isolada (`QApplication` real, offscreen, inspecionando visibilidade/geometria de verdade após cada passo — mesma técnica já usada nesse projeto pra bugs de Qt): `handle_start_library_chat()` e `handle_new_chat()` chamavam `close_library()`/`close_quiz()` **antes** de `_reset_chat_ui()` — e `close_library()`/`close_quiz()` chamam `_show_chat_area()`, que decide o que mostrar (tela de boas-vindas vs. `chat_area` com o scroll) olhando pro `first_message_sent` **ainda da conversa anterior** (que só vira `False` dentro de `_reset_chat_ui()`, chamado depois). Isso faz o `chat_area`/scroll da conversa antiga reaparecer por um instante, com a rolagem antiga, e sumir de novo assim que o reset limpa as bolhas — só que a posição de rolagem obsoleta gruda: a mensagem nova é inserida corretamente na lista, só que fora da área visível. Corrigido invertendo a ordem (`_reset_chat_ui()` sempre roda primeiro, antes de fechar Laboratório/Biblioteca) nas duas funções. Isso expôs um segundo problema, só visível depois do reorder: `activate_chat_layout()` (chamado ao enviar a 1ª mensagem de uma sessão) nunca reexibia o `chat_area` em si, só assumia que ele já estava visível — verdade por acaso no fluxo padrão (já que `chat_area` só é escondido de propósito ao entrar no Laboratório/Biblioteca), mas quebrava depois do reorder porque agora `_show_chat_area()` legitimamente deixa `chat_area` escondido no estado de boas-vindas. Corrigido adicionando `self.chat_area.show()` explícito em `activate_chat_layout()`. Confirmado via reprodução: sem o 2º fix, a mensagem ficava presa pra sempre (nunca reaparecia, nem depois da resposta da IA); com os dois fixes juntos, `chat_area`/`scroll` voltam a `True` e as bolhas aparecem com geometria real assim que a resposta chega — testado tanto pro fluxo "Conversar no chat" quanto pro "Novo Chat" clicado de dentro da Biblioteca (mesmo padrão de bug, mesma correção). Suíte: 239/239 (sem teste novo — é timing de Qt, mesma limitação documentada nos bugs anteriores de layout: o ambiente automatizado confirma o ESTADO final via inspeção de geometria/visibilidade real, mas a confirmação visual definitiva depende do Matheus testando no app de verdade).

- Revisão externa (2026-07-26): mandamos o código pra análise por terceiro (outro chat). Achados reais corrigidos: (1) `latex_sanitizer.py` não limpava LaTeX quando uma potência (`^{2}`) aparecia aninhada dentro de uma raiz (`\sqrt{...}`) — a fórmula de Bhaskara real vazava; corrigido invertendo a ordem de resolução (potência antes da raiz, em loop até estabilizar). (2) `auth.py::verify_password` comparava hash com `==` em vez de `hmac.compare_digest` (timing attack teórico); corrigido. (3) `safety.py` tinha bypass real: "como eu faço para hackear X" não era pego (só "como hackear X" direto); corrigido com prefixo compartilhado (`_HOW_PREFIX`) que cobre a paráfrase em todos os padrões de dano real. (4) `tests/test_groq_tools_live.py` quebrava a coleta do pytest inteira em ambiente sem a lib `groq` instalada; isolado com `@pytest.mark.live` + `pytest.importorskip` (novo `pytest.ini` registra o marker). Suíte em 136/136 (133 sem os testes ao vivo, via `pytest -m "not live"`).
- **Ajustes finais pós-Fusion (2026-07-26).** Depois da troca pra Fusion, 3 pontos reais apareceram: (1) botões de login/configurações (Entrar, Criar perfil, Cancelar, Salvar, Trocar perfil) nunca tiveram estilo próprio — sempre dependeram da aparência nativa do SO — e ficaram "crus" com Fusion; criados `QPushButton#DialogPrimaryButton`/`#DialogSecondaryButton` no `style.qss` e aplicados nos diálogos de login e configurações. (2) Texto digitado como uma única "palavra" longa sem espaço (ex: `asdasdasd...`) não quebrava linha corretamente no balão da mensagem. **1ª tentativa (não funcionou na prática):** texto rico com CSS `overflow-wrap:anywhere` — não reproduzi o bug nos meus testes automatizados, mas o Matheus confirmou rodando de verdade que continuava cortado (suporte a essa propriedade CSS varia entre versões/builds do Qt — não é garantido). **Fix que resolveu:** trocado por uma técnica independente de CSS — [`message_bubble.py`](ui/widgets/message_bubble.py) insere um caractere de espaço de largura zero (invisível) a cada 20 caracteres dentro de qualquer "palavra" sem espaço, antes de exibir. Isso dá ao `QLabel.setWordWrap()` um ponto de quebra real, que funciona em qualquer versão do Qt (não depende de propriedade CSS nenhuma). **Texto centralizado dentro do balão (2026-07-26):** mesmo com a largura calculada certinho, o texto ficava alinhado à esquerda por padrão do `QLabel` — qualquer folga residual (a margem de segurança de 4px) sobrava inteira do lado direito, dando impressão de descentralizado. Adicionado `label.setAlignment(Qt.AlignHCenter | Qt.AlignVCenter)` — a folga (agora bem pequena) fica dividida nos dois lados. Confirmado por medição de pixel: folga esquerda/direita foram de 37px/41px (diferença de só 4px, imperceptível), antes bem mais assimétrico.
**Correção definitiva de largura — cálculo próprio em vez de confiar no QLabel (2026-07-26):** o Matheus apontou dois problemas na mesma imagem: (1) o balão da IA (resposta curta, 2 frases) estava quebrando em ~5 linhas bem curtas, quando cabia em 2; (2) o texto do usuário não ficava "colado" nas bordas — distância maior do lado direito que do esquerdo. Causa raiz: deixar o `QLabel` (`QSizePolicy.Maximum` + `sizeHint()`) decidir sozinho a largura pra texto quebrado é pouco confiável — ele às vezes escolhe uma largura MENOR do que o ideal (espremendo em linhas curtas à toa), não só maior. Corrigido com `_ideal_bubble_width()`: busca binária pela MENOR largura (até o teto) que ainda produz o mesmo número de linhas que a largura máxima — usa `QFontMetrics.boundingRect(..., Qt.TextWordWrap, ...)` pra medir de verdade quantas linhas cada largura candidata produziria. Aplicado tanto pro balão do usuário quanto da IA. Testado: mesmo texto, largura vai de 286px (9 linhas, pouco espaço) a 1122px (2 linhas, bastante espaço) — a altura cai conforme mais espaço fica disponível, em vez de ficar espremida à toa. 4 testes atualizados/novos em `test_message_bubble.py`.
**Correção da folga de texto dentro do balão (2026-07-26):** o Matheus apontou que o texto não ficava colado nas bordas esquerda/direita da caixa do balão — sobrava um respiro visível, maior em balões largos. Causa: a margem de segurança da quebra de linha era uma **porcentagem** (3%) da largura disponível — numa bolha larga (ex: 1000px), 3% vira ~30px de folga real, bem visível. Corrigido: chrome do balão calculado com valor EXATO (54px, somado direto do CSS: padding 18px cada lado + borda 1px cada lado + margem do layout 8px cada lado) e a margem de segurança virou um valor FIXO em pixels (4px, só pra arredondamento de fonte), não mais uma porcentagem — não cresce mais com a largura do balão. Teste de regressão específico (`test_folga_nao_cresce_com_a_largura_do_balao`) garante isso pra qualquer largura futura.
**Correção de corrida (race condition) na largura (2026-07-26):** Matheus reportou larguras inconsistentes entre conversas diferentes (o mesmo tipo de mensagem longa aparecia com larguras bem diferentes dependendo da conversa). Causa: `add_message()` e `handle_load_conversation()` criam os balões chamando `get_max_bubble_width()` ANTES da área de rolagem (`self.scroll`) ter sido exibida e ter o layout assentado (ela só é mostrada 20ms depois, dentro de `animate_first_message_transition`/`activate_chat_layout`) — nesse instante, `self.scroll.viewport().width()` pode retornar um valor provisório, e como nada recalculava depois, esse valor errado ficava permanentemente gravado no balão. Corrigido: `add_message()` e `handle_load_conversation()` agora agendam `QTimer.singleShot(0, self.refresh_bubble_widths)` logo depois de criar os balões, corrigindo a largura assim que o layout assentar. **Nota de transparência:** meu ambiente de teste automatizado (sem tela real) tem limitações conhecidas pra simular timing de redimensionamento de janela de forma fiel — não consegui confirmar 100% a correção por esse meio; a validação real depende do Matheus testando no app de verdade.
**Revisão final v4 (a definitiva):** a v3 forçava largura máxima pra QUALQUER mensagem que precisasse de mais de uma linha — bug novo: uma resposta normal da IA de só 2-3 linhas (frases com espaço de verdade) passou a ocupar a tela inteira, quando deveria abraçar o conteúdo como antes. Restrito: a largura máxima cheia só é forçada quando o texto teve pelo menos um ponto de quebra invisível inserido de verdade (ou seja, só no caso patológico de uma "palavra" única maior que o balão, sem espaço nenhum) — texto normal (qualquer quantidade de linhas, desde que tenha espaços de verdade) o Qt já quebra bem sozinho e o balão continua abraçando o conteúdo, igual sempre foi. 4 testes cobrindo os dois casos, incluindo teste de regressão específico com o texto real que quebrou ("Oi, Matheus! Parece que sua mensagem ficou confusa...").
**Revisão final v3 (Claude/ChatGPT como referência, mas exagerou):** mesmo medindo com precisão (v2), ainda sobrava uma coluna vazia — causa real: `QLabel` não encolhe a caixa pro tamanho exato do conteúdo quando o texto ocupa várias linhas (limitação do próprio widget, não da precisão do cálculo). Um "meio-termo" de largura nunca fecha certinho. Solução: `_needs_wrapping()` decide, por mensagem, se ela cabe numa linha só (aí o balão **abraça o conteúdo**, `minimumWidth=0`) ou se precisa quebrar (aí o balão usa a **largura máxima cheia**, `minimumWidth == maximumWidth`) — nunca um valor no meio.
